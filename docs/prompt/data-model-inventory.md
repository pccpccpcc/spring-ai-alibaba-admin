# 数据架构图与数据字典生成 Prompt

你是一个资深后端架构师、数据建模专家和技术文档设计师。请阅读当前项目中的数据库建表 SQL、迁移脚本、Entity / DO / PO、DTO、枚举和 Repository / Mapper / Service 代码，生成一份“清晰的数据架构总览图 + 完整数据字典”。

## 目标

请输出两份文件：

1. `docs/data-model.md`：完整数据字典和关系说明。
2. `docs/data-model-er.svg`：清晰的数据架构总览图。

要求明确区分两份文件的职责：

- `docs/data-model.md` 负责完整性，覆盖所有数据库表、字段、主键、唯一键、外键、逻辑关联和枚举值。
- `docs/data-model-er.svg` 负责可读性，只展示核心模型、核心字段和关键关系，适合放到 README、技术方案或评审材料中。

## 扫描范围

优先读取以下来源：

1. 数据库建表 SQL / 迁移脚本：
   - 例如 `*.sql`、Flyway / Liquibase 脚本、Docker 初始化 SQL、schema migration。
2. 持久化模型：
   - 例如 JPA Entity、MyBatis / MyBatis-Plus Entity、DO、PO、Record。
   - 重点关注 `@Table`、`@TableName`、`@Id`、`@TableId`、`@Column`、`@TableField` 等注解。
3. DTO / VO / Request / Response：
   - 只在字段语义、JSON 配置结构或枚举含义不清时辅助参考。
   - 不要把所有请求 / 响应 DTO 都当作数据库模型展开。
4. 枚举类和常量：
   - 用来补充状态字段、类型字段、来源字段、启用开关等枚举值。
5. Repository / Mapper / Service / 查询代码：
   - 用来判断逻辑外键、业务关联和 JSON 配置引用。
6. README、配置文件和部署脚本：
   - 用来辅助判断 schema、模块边界和外部存储。

排除构建产物、前端打包产物、缓存目录和无关测试生成物，例如 `target`、`build`、`.gradle`、`node_modules`、`dist`。

## 输出一：`docs/data-model.md`

文档需要包含：

1. 数据来源说明。
2. 图和数据字典的分工说明。
3. 标记说明：
   - `PK`：数据库主键。
   - `UK`：唯一键或唯一业务键。
   - `FK`：SQL 中显式外键。
   - `逻辑 FK`：代码、索引或命名上存在业务关联，但 SQL 没有外键约束。
   - `枚举`：字段有明确枚举值或状态值。
4. 数据模型分组：
   - 按业务域、schema、模块、子系统或聚合根分组。
   - 不要简单按文件路径或表名字母序排序。
5. 每个模型一段一句话说明。
6. 每个模型字段表，格式固定为：

| 字段 | 类型 | 标记 | 说明 |
| --- | --- | --- | --- |

字段表要求：

1. 字段名优先使用数据库字段名；如果 Java 字段名和数据库字段名差异明显，可在说明中补充 Java 字段名。
2. 类型优先使用数据库类型；没有 SQL 时使用 Java 类型。
3. 标出主键、唯一键、显式外键、逻辑外键和枚举。
4. 状态、类型、来源、启用开关等字段要列出枚举值。
5. JSON / TEXT / LONGTEXT 配置字段要说明用途；无法确认结构时写“JSON 配置，具体结构需结合业务实现确认”。
6. 代码里存在但 SQL 未发现的模型要单独列出，不要混入正式数据库表。
7. 如果 SQL 注释和代码枚举不一致，要明确标注差异。

文档末尾必须包含：

1. 显式数据库外键清单。
2. 逻辑外键 / 业务关联清单。
3. 枚举值汇总。
4. 未纳入正式数据库字典的模型或 DTO 说明。

## 输出二：`docs/data-model-er.svg`

请生成“数据架构总览图”，不是完整数据库字段转储图。

图的目标是让产品、前端、后端能快速看懂核心模型边界和关系。可读性优先级高于字段完整性。

### 图的内容规则

1. 按业务域 / schema / 子系统分区：
   - 每个分区用虚线边框和标题标识。
   - 分区标题使用业务语义，例如“账号与工作空间”“应用与编排”“模板与评测”等。
2. 每张表用卡片表示：
   - 卡片头部显示表名。
   - 卡片里只放核心字段，通常 4 到 6 行。
   - 必须显示主键、主要业务键、关键外键、名称 / 状态 / 配置类字段。
   - 不要把所有审计字段都放进图里。
3. 颜色有语义：
   - 同一业务域使用同一色系。
   - 不同业务域使用明显不同的颜色。
   - 使用浅色背景、深色边框和深色文字，保证截图、投影和打印都清晰。
4. 线条有语义：
   - 显式 FK / 强关联：实线箭头。
   - 逻辑 FK / 无数据库约束的业务关联：虚线箭头。
   - 标注 `1:N`、`1:1`、`N:M` 等基数。
5. 底部增加图例：
   - 说明实线、虚线、主键、外键、逻辑外键、颜色分区和关系基数含义。

### SVG 排版规则

不要直接接受 Mermaid 默认 ER 图作为最终结果，除非它确实清晰无重叠。优先使用自定义 SVG、脚本生成 SVG、Graphviz / PlantUML 后处理 SVG，或其他可控布局方式。

SVG 必须满足：

1. 卡片之间不能重叠。
2. 卡片必须完整位于所属分区大框内。
3. 卡片高度必须根据字段数量动态计算，字段不能被裁剪或跑出卡片。
4. 卡片之间要留出足够空隙，避免显得拥挤。
5. 箭头不能被卡片遮住；必要时把关系线绘制在卡片上方，或让箭头终点离开卡片边缘少量距离。
6. 关系标签要有白色或浅色底，避免被线条压住。
7. 容易重叠的关系线要手动绕行：
   - 如果同一张表同时向下连接多张表，不要让多条线共享同一路径。
   - 对跨多层关系使用侧边绕行或外侧绕行。
8. 图例要独立放在底部，不要压住模型卡片或关系线。
9. 画布宁可大一些，也不要为了紧凑牺牲可读性。
10. 生成后检查 SVG 是否存在、非空、可打开。

建议脚本生成 SVG 时增加自动校验：

1. 矩形重叠检测：任意两张卡片不得相交。
2. 分区边界检测：每张卡片必须在对应分区内。
3. 字段高度检测：最后一行字段必须在卡片内部。
4. 元素数量检测：卡片数、关系线数、分区数符合预期。
5. 对已知容易重叠的边设置自定义路由。

## 关系判断规则

请区分三类关系：

1. 显式 FK：
   - SQL 里存在 `FOREIGN KEY` 约束。
2. 逻辑 FK：
   - 字段名明显对应另一张表的业务键，例如 `workspace_id`、`app_id`、`user_id`。
   - Mapper / Service 查询中按这些字段关联。
   - 索引名体现关联关系。
3. 弱引用 / 配置引用：
   - 关系藏在 JSON、TEXT、配置字段中。
   - 图里可以不画，文档中说明即可。

不要把逻辑 FK 写成数据库外键，也不要因为 SQL 没有 FK 就忽略业务关系。

## 工作方式

请按以下步骤执行：

1. 列出所有建表 SQL 和持久化模型文件。
2. 抽取表名、字段、类型、注释、主键、唯一键、索引、外键。
3. 对照 Entity / DO / DTO / 枚举补充字段语义和枚举值。
4. 判断业务分组、核心模型和关键关系。
5. 先生成 `docs/data-model.md`，确保完整覆盖数据字典。
6. 再根据数据字典生成 `docs/data-model-er.svg`。
7. 对 SVG 做排版校验和必要的布局迭代。
8. 最终回复中说明：
   - 生成了哪些文件。
   - 覆盖了多少张表 / 模型。
   - 哪些模型没有纳入正式数据库字典，以及原因。
   - 是否存在 SQL 注释和代码枚举不一致。
   - SVG 是否通过卡片重叠、字段高度、分区边界和文件非空校验。

## 质量标准

1. `docs/data-model.md` 要完整、准确，适合作为数据字典。
2. `docs/data-model-er.svg` 要清晰、好看、适合贴到 README 或技术方案中。
3. 图和数据字典职责分离：
   - 图负责总览和关系。
   - 文档负责完整字段和枚举。
4. 图要有设计感，但不要牺牲准确性。
5. 任何不确定信息都要标注来源或不确定性，不要编造字段或关系。
