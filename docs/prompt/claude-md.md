# CLAUDE.md 生成 Prompt

你是一个资深工程协作助手和代码库维护者。请阅读当前项目已有文档、构建文件、运行脚本、部署配置和核心源码结构，生成一份高质量的根目录 `CLAUDE.md`，用于帮助 Claude / Codex / 后续 AI coding agent 快速理解并安全协作。

## 目标

生成或更新项目根目录：

- `CLAUDE.md`

这份文件应该是“项目入口指南”，不是详细设计文档。它要帮助后续 agent 快速知道：

1. 这个项目是什么。
2. 关键架构和模块在哪里。
3. 事实来源应该优先看哪些文件。
4. 修改代码时要同步哪些文档。
5. 本地怎么跑、怎么检查。
6. 有哪些明确不能碰或暂时空缺的部分。

## 扫描范围

请优先读取：

1. 根目录 README / README-zh / docs 入口文档。
2. `docs/` 下已有架构图、接口清单、数据模型、依赖图等文档资产。
3. 构建文件：
   - Maven `pom.xml`
   - Gradle 文件
   - npm / pnpm / yarn `package.json`
   - monorepo workspace 配置
4. 启动和部署文件：
   - `start.sh`
   - Docker Compose
   - Dockerfile
   - Kubernetes manifests
   - deploy README
5. 核心源码目录结构：
   - 后端模块
   - 前端模块
   - runtime / core / start / openapi 等类似分层
6. 配置文件：
   - `application.yml`
   - 环境变量模板
   - 初始化 SQL

如果项目中存在 `docs/prompt/` 或 `docs/qa/`：

- `docs/prompt/` 通常是可复用 prompt 模板，不要当作项目事实来源。
- `docs/qa/` 通常是概念问答，可作为辅助理解，但不要优先于代码、SQL、README 和正式 docs。

## 输出结构

`CLAUDE.md` 建议使用以下结构：

```markdown
# CLAUDE.md

## 项目定位

## 事实来源优先级

## 核心架构

## 关键模块

## 关键约定

## 文档同步约定

## 怎么跑

## 常用检查命令

## 禁区

## 历史包袱
```

可以根据项目实际增删，但必须保留：

- 项目定位
- 核心架构
- 关键模块
- 关键约定
- 怎么跑
- 禁区
- 历史包袱

其中“禁区”和“历史包袱”如果没有明确事实，请保留空章节，写“待补充”，不要编造。

## 内容要求

### 项目定位

用 1 到 3 段说明项目是什么、解决什么问题、主要面向谁。

要求：

- 不要写成营销文案。
- 不要复制 README 大段内容。
- 如果 README 提到仓库迁移、上游仓库或维护状态，需要简短说明。

### 事实来源优先级

告诉后续 agent 遇到不同问题时优先看哪里。

示例：

- 接口事实：Controller / OpenAPI 定义优先，接口清单是整理结果。
- 数据模型事实：SQL 优先，其次 Entity / DO / Mapper。
- 运行方式事实：README、启动脚本、Docker Compose、部署文档优先。
- 架构关系事实：构建文件、模块依赖、包结构、架构图优先。

### 核心架构

简述后端、前端、中间件、部署形态和主要模块边界。

要求：

- 用项目真实目录名。
- 不要展开每个类。
- 不要把架构图内容复制进来，使用链接指向已有图。

### 关键模块

按业务域列出核心能力。

要求：

- 每个模块 1 行说明即可。
- 不要复制接口清单。
- 容易混淆的概念可以简短提醒，例如“外部访问凭证不是登录会话凭证”“能力包、可执行动作、外部服务是不同抽象”。

### 关键约定

记录后续 agent 改代码时必须尊重的约定。

可包含：

- 语言 / 框架版本。
- 数据访问风格。
- 业务 ID 和数据库 ID 的区别。
- 显式 FK 和逻辑 FK 的区别。
- 文档不复制大段详细内容，只链接。
- 图表生成需要可读性校验。
- 脏工作区不要误删或重置。

### 文档同步约定

说明什么类型改动要同步哪些文档。

示例：

- 改接口：同步接口清单。
- 改表结构 / Entity：同步数据字典和 ER 图。
- 改模块依赖：同步模块依赖图。
- 改外部依赖 / 部署：同步外部依赖图和运行说明。

### 怎么跑

用最少步骤说明本地运行方式。

要求：

- 区分“启动中间件 / 构建项目”和“真正启动应用”。
- 如果依赖 Docker Compose，说明中间件通常是多个独立容器，不需要本机手动安装中间件。
- 如果 README 里访问地址不一致，要如实说明。
- 不要编造未验证的命令。

### 常用检查命令

列出常用验证命令。

示例：

- 后端构建
- 后端测试
- 前端构建
- Docker Compose 状态
- 关键服务日志

只列项目中能从构建文件或 README 支撑的命令。

### 禁区

只写明确事实。

如果没有明确禁区，写：

```markdown
待补充。
```

### 历史包袱

只写明确事实。

如果没有明确历史包袱，写：

```markdown
待补充。
```

## 链接要求

1. 对已有详细文档只放链接，不复制内容。
2. 链接使用相对路径，例如 `[docs/api-list.md](docs/api-list.md)`。
3. 如果链接目标不存在，不要写入；先说明缺失。
4. 不要链接 `docs/prompt/` 作为项目事实入口，除非专门说明它是 prompt 模板目录。

## 校验要求

完成前请检查：

1. `CLAUDE.md` 是否在项目根目录。
2. 文件中引用的相对链接是否存在。
3. 是否误把接口清单、数据字典、SVG 源码、README 大段内容复制进来。
4. “禁区”和“历史包袱”是否没有编造。
5. 运行命令是否能从 README、脚本或构建文件中找到依据。

## 质量标准

1. 精简，适合作为 agent 进入项目后的第一屏上下文。
2. 可执行，告诉后续 agent 看哪里、跑什么、同步什么。
3. 事实准确，不凭空推断。
4. 保留足够链接，让详细内容回到 `docs/`。
5. 不超过必要长度；优先高信号项目约定。
