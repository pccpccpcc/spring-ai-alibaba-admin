# 项目文档维护

当用户要求“更新文档”“检查文档是否过期”“重新生成接口/数据模型/架构说明”“根据现有资料整理项目文档”时使用这个 skill。它的目标是让文档和代码、SQL、配置、脚本保持一致，而不是顺手复制一份源码摘要。

## 适用场景

使用本 skill：

- 扫描 Controller，更新 REST 接口清单。
- 扫描 Entity / DTO / SQL，更新数据字典和数据模型关系。
- 重新生成或修正 ER 图、架构图、模块依赖图、外部依赖图。
- 根据 README、CLAUDE.md、docs/、脚本和配置更新项目说明。
- 检查文档链接、标题编号、目录顺序、遗漏模块。
- 对比代码和文档，找出可能过期的内容。
- 将一次问答沉淀成 QA 文档，或将一次高质量任务沉淀成通用 prompt。

不优先使用本 skill：

- 主要目标是新增、修改、删除业务接口或资源能力。此时先用资源接口变更流程，文档同步作为收尾。
- 主要目标是写产品介绍、营销页面或非代码项目文档。

## 输入信息

优先接受简短输入，并从项目中推断细节。

常见输入：

- 文档类型：接口清单、数据模型、ER 图、架构说明、启动说明、QA、prompt。
- 目标范围：全项目、某个模块、某个目录、某些文件。
- 输出位置：例如 `docs/api-list.md`、`docs/data-model.md`、`CLAUDE.md`。
- 是否需要重生成图片：例如 SVG、Mermaid、PNG。

如果用户没有指定输出位置，优先沿用项目已有文档路径。只有目标范围或输出物不明确时才问一个简短问题。

## 资料优先级

按可信度从高到低使用资料：

1. 源码：Controller、Service、DTO、Entity/DO、Mapper/Repository、配置类。
2. 数据库资料：SQL、migration、初始化脚本、Mapper XML。
3. 自动化资料：测试、CI、Dockerfile、docker-compose、Makefile、脚本。
4. 项目入口文档：README、CLAUDE.md、CONTRIBUTING、`.github/`。
5. 既有 docs 文档。
6. 对话中的解释和临时判断。

当文档和源码冲突时，以源码、SQL、配置为准，并在必要时说明文档被修正的原因。

## 通用流程

1. 明确文档目标和输出文件。
2. 扫描现有文档结构，保留已有风格、标题层级、编号和链接习惯。
3. 扫描权威来源，建立“事实清单”。
4. 对比已有文档，标记新增、删除、变更、可能过期的内容。
5. 更新文档，避免复制大段源码和无关实现细节。
6. 校验链接、标题锚点、文件存在性、图像可读性。
7. 最终回复中说明更新范围、依据来源和未覆盖风险。

## 文档类型

### 接口清单

适用于更新 `docs/api-list.md` 或同类 REST API 文档。

检查项：

- 扫描所有 Controller / API 接口类。
- 识别类级路径、方法级路径、HTTP 方法、权限或认证要求。
- 合并路径变量、query、body、multipart、header 等主要入参。
- 从 DTO、返回包装、泛型、注释、方法名推断返回结构。
- 按模块分组，保持目录编号和标题顺序一致。
- 对测试、mock、example 接口要么收录，要么明确排除原因。
- 完成后用源码反查接口数量，避免遗漏。

### 数据模型和数据字典

适用于更新 `docs/data-model.md`、数据字典或模型说明。

检查项：

- 同时读取 SQL、Entity/DO、DTO、Mapper XML、枚举类。
- 每个模型列出字段、类型、一句话说明。
- 标出主键、外键、唯一键、索引、枚举值、默认值、可空性。
- 区分真实外键、逻辑关联、JSON 配置中的隐式关系。
- 当 SQL 和 Entity 字段不一致时，指出差异或按权威来源修正。

### ER 图 / 架构图

适用于更新 `docs/data-model-er.svg`、架构图、依赖图等图形资产。

检查项：

- 图只展示关键模型和关键关系，不把所有字段塞满。
- 大图要分区，例如业务域、schema、平台能力、外部依赖。
- 卡片之间保持足够间距，箭头和文字不能重叠。
- 字段必须在卡片内，卡片高度要能容纳内容。
- 图片文字要清晰，优先输出 SVG。
- 生成后检查文件非空、尺寸合理、关键节点数量和连线数量符合预期。

### CLAUDE.md / 项目入口文档

适用于更新根目录 `CLAUDE.md` 或同类 agent onboarding 文档。

检查项：

- 保持精简，只写项目定位、核心架构、关键模块、关键约定、怎么跑。
- 详细接口、数据模型、架构图只放链接，不复制正文。
- 空章节可以保留，例如禁区、历史包袱。
- 启动命令要来自 README、脚本、compose、pom、package 配置等事实来源。
- 不确定的内容要写成“待确认”，不要伪装成事实。

### Prompt / QA 文档

适用于维护 `docs/prompt/` 和 `docs/qa/`。

检查项：

- Prompt 应尽量通用，不绑定当前项目的模块名、表名、接口顺序或私有判断。
- Prompt 要说明输入、输出、质量标准和校验步骤。
- QA 只沉淀有复用价值的问题，不把所有对话流水账写进去。
- QA 不是 API 文档的必需前置物；只有当概念容易误解时再补。

## 编辑规则

- 不复制详细源码、长 SQL、完整接口实现，只总结文档所需事实。
- 不把一次性项目结论写进通用 prompt。
- 不为了“完整”塞入低价值细节。
- 不删除用户已有文档结构，除非明确是过期或重复内容。
- 修改图片类文档时，同时确认 Markdown 中的链接仍然有效。
- 如果生成 Mermaid 图，必须渲染预览并确认没有语法错误。

## 验证

按文档类型选择验证：

- 用 `rg` 反查 Controller、Entity、SQL、DTO 是否覆盖。
- 检查 Markdown 链接目标是否存在。
- 检查标题编号和目录锚点是否匹配。
- 检查 SVG 文件非空、尺寸合理、关键文本可搜索。
- 对接口清单，抽样核对方法、路径、入参、返回结构。
- 对数据模型，抽样核对字段类型、主键、外键、枚举值。

如果无法完整校验，要说明未校验范围和风险。

## 最终回复

回复用户时说明：

- 更新了哪些文档文件。
- 本次依据了哪些主要事实来源。
- 做了哪些校验。
- 是否有刻意排除或仍需人工确认的内容。
