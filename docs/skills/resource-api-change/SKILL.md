# 资源接口变更

当用户要围绕某个业务资源调整接口时使用这个 skill。它不是只新增一个 Controller 方法，而是把接口层、业务层、数据模型、持久化、测试和文档一起对齐。

## 最小输入

只向用户确认真正缺失的必要信息。其他内容优先从代码库现有实现中推断。

必填：

- 模块名：业务域或功能模块，例如账号、插件、知识库、Prompt、订单。
- 资源名或表名：可以是表名、实体名、Controller 资源名或业务对象名。
- 操作类型：新增、查询/查找、修改、删除、字段变更、状态流转、批量操作、关联操作、导入导出。

可选：

- 库名 / schema：只有在项目存在多个库、多个 schema，或者表名有歧义时才需要。

如果用户给的信息少于上述内容，先扫项目。只有在目标资源或操作仍然不明确时，才问一个简短问题。

## 第一轮扫描

1. 定位目标模块的现有代码：
   - Controller / API 接口。
   - Service / ServiceImpl / Manager。
   - Entity / DO / PO。
   - DTO / Request / Response / VO。
   - Mapper / Repository / Mapper XML。
   - SQL / migration / 初始化脚本。
   - 测试。
2. 识别本项目约定：
   - URL 前缀和命名风格。
   - HTTP 方法使用习惯。
   - 统一返回包装和分页对象。
   - 异常处理和参数校验方式。
   - 数据访问方式：MyBatis-Plus、MyBatis XML、JPA，或混合模式。
   - 逻辑删除、workspace/account 隔离、状态字段、审计字段。
3. 修改前先读附近的相似资源。优先复用项目已有模式，不引入新的通用 CRUD 框架。

## 操作分支

### 新增

适用于新增资源、创建接口或补齐创建能力。

检查项：

- 如果涉及持久化，新增或修改表结构 / migration。
- 新增或修改 Entity / DO / PO。
- 新增或修改 DTO / Request / Response。
- 按模块现有模式新增 Mapper / Repository / XML。
- 新增 Service 方法和实现。
- 新增 Controller 接口。
- 补齐参数校验、默认值、唯一性校验。
- 如果附近已有测试模式，补测试。

### 查询 / 查找

适用于详情、列表、分页、条件过滤、模糊搜索、批量查询、关联查询、统计查询、导出查询。

检查项：

- 复用现有查询对象和分页风格。
- 筛选逻辑放在 Service / Mapper，不堆在 Controller。
- 如果资源有 workspace/account 隔离，查询条件必须带上隔离约束。
- 关联查询要避免明显的 N+1 查询。
- 如果实体包含密钥、内部配置、敏感字段，返回 DTO 要显式裁剪。

### 修改

适用于全量修改、局部修改、配置修改、重命名、状态更新、字段级调整。

检查项：

- 判断是否影响已有客户端兼容性。
- 除非本项目已有约定允许，否则不要修改 ID、创建人、创建时间等不可变字段。
- 状态类修改要先校验状态流转是否合法。
- DTO、Entity、Mapper 映射要保持一致。
- 如果字段语义变化，补 migration / 数据回填说明。

### 删除

适用于逻辑删除、物理删除、批量删除、移除接口或移除字段。

检查项：

- 先判断模块使用逻辑删除还是物理删除。
- 删除前检查子资源和引用关系。
- 删除接口前搜索前端、OpenAPI、调用方。
- 移除能力默认视为破坏性变更，除非确认只在内部使用。

### 字段变更

适用于新增字段、删除字段、字段改名、类型变化、枚举值变化、默认值变化。

检查项：

- 更新 SQL / migration。
- 更新 Entity / DO / PO。
- 更新 DTO 和映射逻辑。
- 如果有 Mapper XML，更新 resultMap、SQL 片段和字段列表。
- 更新枚举类和参数校验。
- 持久化字段变更后，同步数据模型文档。

### 状态流转

适用于发布、启用、停用、归档、停止、重启、测试、审批、拒绝等操作。

检查项：

- 明确允许的来源状态和目标状态。
- 如果本项目偏好显式动作接口，使用清晰的动作路径。
- 状态校验放在 Service 层。
- 更新枚举说明和接口文档。

### 批量 / 关联 / 导入导出

适用于批量新增、批量修改、批量删除、绑定、解绑、查询关联资源、导入、导出、模板下载。

检查项：

- 明确事务边界。
- 明确单项失败时的响应结构。
- 避免把关键关系偷偷塞进 JSON 配置字段，除非这是项目既有设计。
- 文件类接口要写清 multipart、流式返回或二进制返回结构。

## 编辑规则

- 不要一上来设计新的通用 CRUD 框架。
- 变更尽量收敛在目标模块内，只有共享契约确实需要变化时才改公共代码。
- 优先使用项目已有 helper、返回包装、分页对象和异常类型。
- 保留工作区里用户已有改动，不回滚无关文件。
- 如果影响持久化数据，同步 SQL 和数据模型文档。
- 如果影响 REST 接口，同步接口文档。

## 文档同步

代码改完后：

- Controller 方法、路径、DTO、返回结构变化时，更新 `docs/api-list.md`。
- SQL、Entity/DO、Mapper XML、枚举或持久化语义变化时，更新 `docs/data-model.md`；关系结构变化时同步 `docs/data-model-er.svg`。
- 模块边界、启动方式、部署假设变化时，只在 `CLAUDE.md` 中补短说明和链接。

更新 `docs/api-list.md` 时，要用源码反查方法和路径覆盖率。故意排除测试、mock、示例接口时，要写明原因。

## 验证

按变更风险选择验证方式：

- 编译受影响模块，或编译整个后端。
- 如果附近有测试，运行相关测试。
- SQL 变更后，核对表字段、实体字段、Mapper 字段是否一致。
- 文档同步后，确认链接存在、生成文件非空。

通用命令示例，按项目实际情况调整：

```bash
mvn test
mvn clean install -DskipTests
```

如果无法运行验证，要说明原因和剩余风险。

## 最终回复

回复用户时说明：

- 变更了哪个资源、哪类操作。
- 按层列出修改文件：Controller、Service、DTO、Entity/DO、Mapper/Repository、SQL、文档、测试。
- 运行了哪些验证，结果如何。
- 是否存在兼容性风险或迁移风险。
